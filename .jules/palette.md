## 2024-05-12 - Accessible Icon Buttons
**Learning:** Using ligature-based icon fonts (like Material Icons) inside interactive elements causes screen readers to read the ligature string (e.g., "visibility_off") instead of the element's purpose, completely breaking the UX for screen reader users.
**Action:** When using icon-only buttons, ALWAYS add an `aria-label` to the `<button>` explaining the action, and ALWAYS add `aria-hidden="true"` to the inner icon element. Also, use `aria-pressed` to communicate toggle states.
## 2024-05-14 - Accessible Framer Motion Icon Buttons
**Learning:** Icon-only interactive elements using framer-motion (e.g., `<motion.button>`) require explicit `aria-label`s for screen readers. The inner icon element itself (like `<span className="material-icons">add</span>`) needs `aria-hidden="true"` to prevent redundant or confusing announcements, and focus rings (`focus-visible:ring-...`) must be maintained so keyboard users have a visible focus indicator without relying strictly on mouse hover animations.
**Action:** When implementing icon-only buttons using framer-motion, always provide `aria-label`, hide the inner decorative icon with `aria-hidden="true"`, and include `focus:outline-none focus-visible:ring` tailwind utility classes.
## 2024-05-16 - Accessible Table Inputs
**Learning:** Form inputs embedded directly within data tables (like checkboxes and quantity inputs) often lack explicit visual `<label>` elements due to space constraints and table header context. This leaves screen reader users without context for what the input modifies.
**Action:** Always provide dynamically generated `aria-label` attributes to form inputs within tables (e.g., `aria-label={"Quantity for " + item.name}`) to provide essential context for assistive technologies.
## 2024-05-18 - Loading State and Focus Styles on Action Buttons\n**Learning:** Interactive buttons that perform async actions (like the "Optimize Prices" button in the dashboard) often lack proper visual feedback during loading states, keyboard focus styling, and appropriate `aria-hidden` attributes for decorative icons. \n**Action:** When implementing action buttons, ensure they have: 1. a visual loading indicator (e.g., spinning icon) during async operations. 2. `focus:outline-none focus-visible:ring-...` for keyboard navigation. 3. `disabled` states with visual cues (`opacity`, `cursor-not-allowed`). 4. `aria-hidden="true"` on inner decorative icons.
## 2024-05-19 - Accessible Custom Input Containers
**Learning:** When styling inputs with custom wrapper elements (e.g., using `focus:outline-none` on the `<input>` and styling the parent `<div>`), the wrapper will not naturally show focus when the input is active, causing keyboard users to lose track of their position. Additionally, search inputs inside such wrappers without adjacent visual `<label>`s provide no context to screen reader users.
**Action:** When building custom input containers, always add `focus-within:ring` classes to the parent container to restore visual focus states. Provide an explicit `aria-label` to the input element if a visual label is not present, and hide decorative icons using `aria-hidden="true"`.
## 2024-05-20 - Accessible Custom Tablists
**Learning:** When building custom tab interfaces using simple `<div>` and `<button>` elements, screen readers do not understand the relationship or state of the tabs. Additionally, custom tabs often lack proper keyboard focus styling.
**Action:** Always wrap custom tab buttons in a container with `role="tablist"` and an `aria-label`. Add `role="tab"` to the individual buttons, use `aria-selected` to communicate the active state, and ensure `focus:outline-none focus-visible:ring-*` classes are present for keyboard accessibility.
## 2026-10-04 - Preventing Layout Shift in Custom Tabs
**Learning:** When building custom tab interfaces where the active state includes a border (like `border-b-2`), the absence of this border on inactive tabs causes a slight visual layout shift (jank) when switching between tabs, making the interface feel less polished.
**Action:** Always apply a transparent border (`border-transparent`) of the exact same width (e.g., `border-b-2`) to inactive tab states to reserve space and prevent layout shifts upon state changes.
